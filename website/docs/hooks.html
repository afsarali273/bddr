bddr / Writing tests

Hooks

Hooks run setup and cleanup code around your tests. bddr has the same levels as TestNG, from the whole run down to a single step.

The levels

LevelHooksRuns
RunBeforeAll, AfterAllOnce, in the main process. Aliases: BeforeSuite, AfterSuite.
WorkerBeforeWorker, AfterWorkerOnce per process that runs scenarios. With the inline pool that is once per run.
GroupBeforeGroup, AfterGroupBefore the first member and after the last member.
FeatureBeforeFeature, AfterFeatureBefore the first and after the last scenario of the feature.
RuleBeforeRule, AfterRuleThe same, for a Rule.
ScenarioBefore, AfterEvery scenario attempt. Aliases: BeforeScenario, AfterScenario.
StepBeforeStep, AfterStepAround every step.

Write a hook

The first argument is either a function or an options object (or a tag expression string) followed by the function.

Options

OptionWhat it does
tagsOnly run for scenarios whose tags match. A string alone is shorthand for it: After('@ui', fn). For feature hooks the filter sees the feature's tags, and for rule hooks the rule's tags. BeforeGroup('@group:checkout', fn) picks a group.
orderLower numbers run first for Before hooks. After hooks run in reverse order. Default 0.
alwaysRunFor Before hooks: run even if an earlier hook at this level failed.
timeoutMsTime budget for the hook.
nameShown in reports and errors.
eachAttemptStep hooks only: run around every repeat or retry of a step, not once per step.

What happens when a hook fails

  • If a Before hook fails, the scenario's steps are skipped and the scenario fails. After hooks still run, so cleanup is not lost.
  • A failing After hook fails the scenario.
  • If BeforeAll fails, no scenario starts.
  • Failures of run, worker and group hooks appear in the console under "Hook failures".

Clean up with defer

For cleanup that belongs to one thing you created, ctx.defer keeps it next to the code that created it.

Hooks and the process pool

With pool: 'process', feature, group and rule hooks run once in every process that runs a member. Put per-process resources, such as a browser, in BeforeWorker or, better, in a worker-scoped fixture.

Tip

If you find yourself writing a Before hook that creates a thing and an After hook that closes it, write a fixture instead. A fixture is created only when something uses it and always cleaned up.
