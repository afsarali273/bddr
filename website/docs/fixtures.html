bddr / Writing tests

Fixtures and inject()

A fixture is a named value that bddr creates when a step first asks for it and cleans up afterwards. Browser pages, API clients and page objects all work this way.

Define a fixture

The declare module block gives ctx.page, ({ page }) and inject('page') their types. You normally do not write this yourself. The Playwright plugin ships it.

Scopes

ScopeLifetime
'scenario' (default)One per scenario attempt. A retry gets a fresh one. Cleaned up when the scenario ends.
'feature'One per feature in a worker process, created on first use and cleaned up when the feature ends. A @serial feature runs in one worker process, so all its scenarios share the value.
'worker'One per worker process, created on first use and cleaned up after the AfterWorker hooks. With the inline pool that is one for the whole run.

A fixture may use fixtures of the same or a longer scope: a scenario fixture can use a feature or worker fixture, never the other way round. Feature and worker fixtures can add afterScenario(value, { status, error, ctx }), called after every scenario that used them. Use it to take a screenshot of a shared page after each failed scenario.

Request a fixture

bddr reads the first parameter of a step, a hook or a fixture setup and creates the fixtures you name there before the code runs. This is the same idea as Playwright Test.

Warning

A helper function that reads ctx.page inside its body is invisible to bddr. If the page was not created yet you get the error "Fixture 'page' is asynchronous and was not requested before use". Destructure the fixture in the step that calls the helper, or use await ctx.fixture('page') inside it.

Order of cleanup

Fixtures are cleaned up in reverse creation order, after the steps, the After hooks and ctx.defer callbacks. Cleanup receives the scenario's final status and error. If a cleanup throws, the scenario fails, with a hook named "fixture teardown".

Rules for names

Fixture names are identifiers. They cannot clash with built-in context properties such as state, params or log. Defining the same name twice is an error.
