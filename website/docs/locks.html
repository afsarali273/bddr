bddr / Orchestration

Locks and priority

Parallel runs break when two tests change the same thing at once. Locks keep those tests apart. Priority decides what starts first when there is a choice.

Locks

Give the scenarios that share a resource the same lock name. Scenarios with the same lock never run at the same time, even on different workers. Scenarios with different locks, or none, are not affected.

To lock a whole group, list the lock in the config. Every member holds it.

Tip

Name locks after the thing they protect, such as payments-db or admin-user, not after the test.

Exclusive

Use @exclusive for a scenario that must run with nothing else running, such as one that restarts a service. A group with mode: 'exclusive' does the same for its members.

Priority

When more scenarios are ready than workers are free, bddr starts the one with the lowest priority number first. The default is 0.

  • A scenario's @priority wins over its group's priority.
  • With several groups, the lowest group priority applies.
  • Priority never breaks a dependency. A scenario still waits for what it depends on.

Use a negative priority to put slow or important scenarios first, so they do not start last and stretch the run.
