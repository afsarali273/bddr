bddr / Orchestration

Sharding in CI

Sharding lets four CI machines each run a quarter of the suite. bddr splits the work so that scenarios that belong together stay on the same machine.

Run one shard

Every machine uses the same command with its own number, from 1/4 to 4/4. The split is deterministic, so all machines agree without talking to each other. bddr plan --shard 1/4 shows what a shard would run.

What stays together

Scenarios are never split across shards when they are linked by:

  • a dependency, hard or soft,
  • the same named group,
  • the same lock,
  • a @serial feature.

Each linked set is one unit. Units are packed onto shards, largest first, by their average duration from the run history. Without history every scenario weighs the same. A shard with nothing to run exits with 0.

Big units

If one unit holds most of the suite, one shard ends up with most of the work. bddr warns about this. Use more locks, fewer dependencies or smaller groups to break it up.
