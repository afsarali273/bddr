UI and API in one scenario

A scenario can create data through the API and check it in the browser, or the other way round. Install both plugins and ask for the fixtures you need in each step.

Set up both plugins

The fixture names do not clash. Use page, request or driver for the browser and api for HTTP. Use Selenium instead of Playwright the same way.

A scenario that uses both

Values travel between the two kinds of step in the scenario state, ctx.state. The browser is started only in the steps that ask for page. A scenario that only uses api never opens one.

Useful combinations

  • Data from the API, check in the UI. Create records quickly through the API, then check how the page shows them.
  • The UI and the API agree. Request a page through api and open it in the browser, then compare the status.
  • Sessions across both. Sign in through the API and put the token in the browser's storageState or a cookie.
  • Clean up through the API. Delete test data with ctx.defer after a UI test.

Keep them apart when you can

A scenario that is only about the API should not need a browser, and a UI scenario should not depend on API details. Use mixed scenarios for the places where the two meet. Put API-only scenarios and UI-only scenarios in separate groups so they run at the speed that suits each.

The complete working version is examples/playwright-showcase/features/mixed/ui-and-api.feature, with 8 mixed scenarios.
