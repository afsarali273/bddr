bddr / Introduction

Architecture

bddr is four small packages and a set of plugins. A run is a short pipeline: parse, select, plan, schedule, run. Everything it does is reported as events, and the reporters only read those events.

The big picture

You give bddr feature files and a config. The runner plans the run, schedules it on workers and writes reports. Browsers and HTTP clients come from plugins, not from the runner.

Packages

The runner is split so that each part has one job and the dependencies point one way: down.

PackageOwnsDepends on
@bddr/coreThe spec model, stable scenario ids, tags, selection, the plan, data file loading, run history and the event schema.Only the Cucumber parsing libraries, behind adapters.
@bddr/runtimeSteps, hooks, fixtures, the context, the scheduler, the inline and process pools, retries and the plugin API.@bddr/core and the Cucumber expressions library.
@bddr/reportersConsole, HTML, JUnit, Cucumber JSON, Messages, NDJSON and living docs.@bddr/core. Reporters read events and never call the runtime.
@bddr/cliThe bddr command, config loading, watch and debug modes, and the worker entry point.The three packages above.

Why the Cucumber libraries are replaceable

bddr uses Cucumber's libraries only to parse Gherkin, tag expressions and step expressions. Each one sits behind an interface in an adapters folder, so the runner does not depend on how they work. This also lets other spec formats be added later as extra parsers.

The life of a run

Every bddr run goes through the same stages. The first three only deal with data, so they are fast and easy to test.

  1. Parse

    Feature files become scenarios. Each scenario gets a stable id that does not change when you edit other parts of the file. See Feature files.

  2. Select

    Paths, tags, names and ids choose what to run. Scenarios that a selected scenario depends on are added automatically. See Tags and selection.

  3. Plan

    Groups, dependencies, locks and priorities become one plan. You can read it first with bddr plan. See Groups and Dependencies.

  4. Schedule

    The scheduler gives ready scenarios to free workers, holds locks, and applies retries. See Locks and priority and Retries and flaky tests.

  5. Run

    A worker runs the hooks and steps for one scenario, creating fixtures when a step asks for them. Every stage reports what happened as events, and the reporters turn those events into files. See Reporters and Event reference.

Workers

By default the workers are concurrent async tasks in one Node.js process. With pool: 'process' each worker is its own process. The plan and the scheduler stay in the parent in both cases, so groups, locks and dependencies behave the same.

Plugins and fixtures

A plugin registers fixtures when bddr starts. A fixture is created when a step first asks for it and closed when its scope ends, so a browser only starts if some scenario needs one.

Because a plugin only registers fixtures, one scenario can use several of them, for example a browser and an API client. See How plugins work, Fixtures and inject() and UI and API in one scenario.

Why it is built this way

  • The plan is data. You can print it, test it and split it across CI machines before a single browser opens.
  • Reporters read events. A new report format does not need changes to the runner.
  • Core has no browser or HTTP library. The plugin and the library it wraps are dependencies of your project, so you choose the versions.
  • One configuration and one event schema. A planned Java port will use the same ones, so the same specs and reports work on both.
