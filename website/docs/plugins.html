bddr / Plugins

How plugins work

A plugin bundles fixtures, hooks, steps and parameter types. bddr core depends on no browser or HTTP library. The plugin and the library it wraps are dependencies of your project.

The plugins that ship with bddr

PluginWrapsFixturesPage
@bddr/playwrightPlaywrightbrowser, context, page, request, expect, newContext, playwrightPlaywright
@bddr/seleniumselenium-webdriverdriver, open, wait, newDriver, seleniumSelenium
@bddr/axiosaxiosapi, newApi, axiosaxios

They live in plugins/ in the repository. Each is a separate package, not part of the bddr workspace, so the bddr packages never depend on Playwright or Selenium.

Add one to your project

  1. Install the plugin and the library

    Until bddr is published, install the plugin from your clone. The command for each plugin is on its page and in Getting started.

  2. List it in the config

    Without TypeScript types you can write the plugin by name: plugins: [['@bddr/axios', { baseURL: '...' }]].

  3. Import it once for types

    This types ctx.api, ({ api }) and inject('api') in your step files.

  4. Use the fixture

Several plugins together

List as many as you need. Their fixture names do not clash, so one scenario can drive a browser and call an API. See UI and API in one scenario.

Options from the command line

Plugins read run-time overrides from -D, such as -D browser=firefox, -D headed=true or -D baseURL=https://staging.example.com. Each plugin page lists them.

Plugin facts

  • A plugin's setup runs once per process, in the main process and in every worker process, before your step files load.
  • A name is looked up from the config folder. Paths that start with . are relative to the config file.
  • A missing plugin is a usage error and the run exits with code 2.
  • A scenario that uses none of a plugin's fixtures starts nothing from it. An API-only scenario never opens a browser.
