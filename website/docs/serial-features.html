bddr / Orchestration

Serial features

Mark a feature @serial when its scenarios form a journey. They run one after another in file order, while other features keep running beside it.

The basics

"Pay" starts when "Add to basket" has finished, whether it passed or not. "See the receipt" follows "Pay". Other features and other groups run in parallel as usual, so two serial features run side by side, each in its own order.

Where you can put it

WhereEffect
@serial on a FeatureEvery scenario waits for the previous one.
@serial on a RuleOnly that rule's scenarios are chained.
Config featureMode: 'serial'Every feature is serial. Add @parallel to a feature to opt it out.

Rules worth knowing

  • The order is file order. Outline and data rows run in row order.
  • A failed scenario does not stop the next one. The chain orders; it does not depend. Add @dependsOn:id when a scenario really needs an earlier one to pass.
  • Groups, locks, priorities, retries and @exclusive still apply. A scenario retry finishes before the next scenario starts.
  • If you select a subset with -t, --name, file:line or --rerun-failed, only the selected scenarios are chained.
  • --shard keeps a serial feature on one shard.

Errors, exit code 2

@serial on a single scenario, @serial together with @parallel, and a scenario that depends on a later scenario in the same serial feature.

Share one browser session

Serial features are the natural place to log in once and keep the page open. The browser plugins support this with a tag on the feature.

Use @freshContext on a scenario to leave the shared context.

Use @freshSession on a scenario to leave the shared session.

With pool: 'process' every scenario of a serial feature runs in the same worker process, so the session survives between them. Under the hood this uses a feature-scoped fixture. See Fixtures and inject().

Warning

A retried scenario continues on the shared page, not on a fresh one. Start each scenario from a known URL.

See the chain in the plan

npx bddr plan shows each chained scenario with <- previous (feature runs in file order).
