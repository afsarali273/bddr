bddr / Orchestration

Retries and flaky tests

A retry gives a failed test another chance. bddr still tells you it failed first, so retries do not hide flaky tests.

Retry a scenario

Use @noRetry to turn retries off for a scenario when the config enables them.

on limits retries to errors whose name or message matches. Without it every failure is retried.

Each attempt starts with fresh scenario state and fresh scenario-scoped fixtures. The report shows every attempt.

Flaky, not just passed

A scenario that fails and then passes on a retry is reported as flaky. The run passes, unless you ask otherwise:

With history: true in the config, bddr records every run in .bddr/history and gives each scenario a flakiness score: the share of runs whose outcome flipped or that passed only after a retry. A scenario that always fails scores 0, because it is broken, not flaky.

Quarantine

Add @quarantine to a test you know is broken but want to keep running. It runs and is reported, but a failure never fails the build. JUnit XML shows a quarantined failure as skipped.

Retry a group

When members depend on each other, retrying one is not enough. Retry the group instead.

retryMembers is 'all' or 'failed'. Groups that depend on this one wait until it settles.

Retry a worker crash

If a worker process crashes, only its scenario fails and the lane starts again. To retry the scenario on a fresh process, set retry.workerCrash or pass --worker-crash-retry 1.

Re-run only what failed

The first run writes the event stream. The second runs only scenarios that did not pass, plus what they depend on. bddr report merges the files, and later runs win.

Retry a step

For one slow call, retry the step instead of the scenario. Put the tags at the end of the step line.

Defaults for every step of a scenario are @stepRetry:N, @stepDelay:2s and @stepTimeout:10s.
